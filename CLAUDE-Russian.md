## Отложенная задача (добавлено 2026-08-06, не начата)

По указанию пользователя есть план по исследованию возможности внедрения
технологии Toshiba Simulated Bifurcation Machine (псевдоквантовые

оптимизации для этого репозитория пока не определено — исследование
отложено до будущей сессии.

## Роль этого проекта

Кроссплатформенный слой совместимости DirectX (D3D9/10/11/12), цель
которого — запускать существующие приложения/игры, написанные для
Windows-only API DirectX, на Linux, Android, а в перспективе на macOS и
семействе PlayStation.

2026-07-25, по явному выбору пользователя, проект взял курс на
преследование **настоящего слоя совместимости в обратном направлении**
(запуск немодифицированных Windows DirectX-бинарников/шейдеров на других
ОС), а не более ранней альтернативы «предоставлять DirectX-подобный API
поверх Vulkan как общей базы».

## Коррекция технического позиционирования (2026-07-25, важно)

Более ранняя оценка (2026-07-23) полагала, что DXVK/vkd3d-proton/MoltenVK
транслируют только в одном направлении (DirectX → Vulkan/Metal) без
реального примера обратного направления, и потому были плохим техническим
выбором. Это было **смешением двух разных осей** и было скорректировано:

- DXVK/vkd3d-proton (технология, стоящая за Proton от Valve / совместимостью
  Linux Steam с DirectX-играми) и MoltenVK-based CrossOver/Whisky (macOS)
  являются реальными, работающими примерами именно того обратного
  направления совместимости, которое хочет пользователь: запуск реальных
  существующих DirectX-бинарников/игр (Windows-only API) без изменений на
  Linux/macOS.
- **Направление трансляции** («вызовы DirectX транслируются в вызовы
  Vulkan») и **направление пользовательского опыта** («работает ли
  Windows-ориентированное DirectX-приложение реально на Linux/macOS») —
  это отдельные оси — то, что первое ориентировано на Vulkan, не мешает
  второму корректно достигать «DirectX работает на другой ОС».
- Следовательно, использование Vulkan в качестве внутреннего исполнительного
  бэкенда не противоречит преследованию настоящего слоя совместимости в
  обратном направлении — DXVK и подобные являются именно этим прецедентом.
  Этот проект принимает тот же подход: перехват вызовов API D3D +
  трансляция байткода шейдеров DXBC/DXIL во время выполнения → исполнение
  через Vulkan.

## Охват и честная дорожная карта

**Фаза 0 (текущая, стадия проектирования/исследования)**:
- Исследование структуры DXBC/DXIL (форматов байткода шейдеров DirectX).
- Изучение архитектуры существующих реализаций с открытым исходным кодом
  (DXVK, vkd3d-proton,
  [dxil-spirv](https://github.com/HansKristian-Work/dxil-spirv) —
  фактический инструмент трансляции DXIL→SPIR-V, используемый
  vkd3d-proton — SPIRV-Cross, naga), чтобы избежать изобретения велосипеда
  и позаимствовать проверенные проектные решения.
- Выделение реалистичного охвата MVP: **полный графический конвейер
  (растеризатор, сэмплер текстур, состояние блендинга и т. д.) пока вне
  охвата.** Начать только с вертикального среза, охватывающего
  диспетчеризацию D3D11 Compute Shader (DirectCompute) — один простой
  вычислительный шейдер, реально оттранслированный из DXBC/DXIL в SPIR-V,
  диспетчеризованный через `opencuda-vulkan` от `open-cuda`, и проверенный
  на численное совпадение с эталонной CPU-реализацией. Работа над
  графическим конвейером начинается как следующая фаза только после того,
  как этот вертикальный срез действительно заработает.

**Фаза 1 и далее (не начаты)**:
1. Вертикальный срез D3D11 Compute Shader (трансляция DXBC/DXIL→SPIR-V +
   диспетчеризация Vulkan).
2. Минимальный графический конвейер D3D11 (вершинные/пиксельные шейдеры +
   базовая растеризация).
3. Поддержка D3D12 (списки команд, кучи дескрипторов, корневые сигнатуры).
4. Поддержка Android (сам Vulkan нативен для Android, поэтому большую
   часть активов версии Linux следует переиспользовать — но скорее всего
   понадобится слой эмуляции Win32/COM, эквивалент Wine; в этом случае
   рассмотреть сотрудничество/переиспользование самого проекта Wine).
5. Поддержка macOS / iPhone / iPad (через MoltenVK, тот же подход, что и
   CrossOver/Whisky; iPhone/iPad требует Apple Developer Program для
   официального распространения — нативное выполнение на неофициальном
   оборудовании невозможно, то же ограничение, выявленное в исследовании
   `dream-os`).
6. Различные UNIX-семейства систем (BSD и т. д.) — вероятно, можно
   переиспользовать большую часть пути Linux в зависимости от поддержки
   Vulkan (пока не исследовано).

**О поддержке PlayStation 4/5/6/7 (честное раскрытие, по состоянию на
2026-07-25)**: входит в изначальный замысел пользователя, но

## Базовые проекты (по указанию пользователя, 2026-07-25)

- **[open-cuda](https://github.com/aon-co-jp/open-cuda)**: использует
  `opencuda-vulkan` (бэкенд выполнения Vulkan Compute, проверенный на
  реальном оборудовании NVIDIA GT 730) как исполнительный бэкенд шейдеров.
  Планирует переиспользовать абстракцию `opencuda-core::GpuDevice`
  (alloc/memcpy/launch_kernel) как есть, передавая ядра, оттранслированные
  DXBC/DXIL→SPIR-V, как `KernelSource::SpirV` (точные детали API нужно
  подтвердить по `opencuda-core`). Отличается от `opencuda-directx`
  (Windows-only бэкенд D3D12, Фазы 1&2 уже реализованы) — тот выполняет
  DirectX нативно *на* Windows, противоположное направление относительно
  этого проекта (запуск DirectX *на других ОС*).
- **[aruaru-llm](https://github.com/aon-co-jp/aruaru-llm)**: в настоящее
  время нет прямой технической зависимости (aruaru-llm — сервис вывода
  LLM; этот проект — слой совместимости графического API). Точное
  намерение, стоящее за упоминанием aruaru-llm пользователем как «базового»,
  не подтверждено — возможно, имеется в виду следование общему паттерну
  сервисации «клонирования/арендаторов» (например, применение паттерна
  управляющего API в стиле `TenantRegistry` к какой-то управленческой
  поверхности этого проекта, такой как сервер кэша трансляций). Будет
  обновлено по мере выявления конкретных точек интеграции.

## Политика разработки (сводка по всей экосистеме)

- Основа — реализация на Rust. Используются крейт `windows` (Windows API)
  и Vulkan-биндинги (`ash` и т. д., соответствующие тем, что использует
  `opencuda-vulkan`).
- «Никогда не сообщать о готовности только на основании успешной
  проверки типов/сборки» — сообщать о работоспособности чего-либо только
  после реальной трансляции реального байткода DXBC/DXIL, диспетчеризации
  через реальный Vulkan и подтверждения численного совпадения с эталонной
  CPU-реализацией на реальном оборудовании (дисциплина, общая для всей
  экосистемы).
- Нереализованные/заглушечные функции никогда не должны ложно сигнализировать
  «поддерживается» (следуя паттерну `supports_dxil()` из `opencuda-directx`).
- Согласовывать с пользователем перед любым решением, связанным с новыми
  файлами, новыми крейтами, новыми репозиториями или суждениями о
  наименовании/размещении (урок 2026-07-23, см. `CLAUDE.md` `open-raid-z`).

## HANDOFF (только самые свежие записи — полный журнал см. в CLAUDE.md)

- **2026-08-20: реализован и проверен на реальном железе вертикальный
  срез compute shader для GEMM (фиксированный 2x2)** — первый шаг к
  аппаратному ускорению LLM-инференса. В `directx-shader-translate`
  добавлена функция `translate_gemm2x2_shader`: HLSL-шейдер GEMM 2x2x2
  был реально скомпилирован через `fxc.exe`, его DXBC декодирован,
  переведён в SPIR-V и запущен на реальном Vulkan (NVIDIA GT 730) с
  использованием контракта ядра `opencuda-vulkan`. Результат GPU точно
  совпал с эталонным CPU-умножением матриц. Честное ограничение:
  только фиксированный размер 2x2 — общий GEMM переменного размера (с
  циклами), операции Attention и подключение к `aruaru-llm` остаются
  вне рамок.
- **2026-08-19: исследована целесообразность механизма автообновления
  (по образцу self-update через GitHub Releases в `open-english`) —
  отложено.** Единственный бинарник с `fn main` в workspace —
  `directx-graphics-window` (демо в стиле Breakout для визуальной
  проверки) без постоянно работающей службы и без эндпоинта
  `/healthz`, поэтому паттерн неприменим.
- **2026-08-19: рассмотрено утверждение, что «отсутствие постоянной
  службы — это недостаток» — вывод: нет.** Настоящий Microsoft DirectX
  распространяется в виде runtime-DLL, которые приложения динамически
  линкуют, а не как независимая фоновая служба; текущий дизайн (только
  библиотека + демо-бинарник) соответствует архитектуре оригинального
  DirectX.
- **2026-08-20: зафиксирована идея-заметка `open-cg-cad` (не начато).**
  Концепция будущего инструмента 3D-моделирования с захватом движения,
  изменением спецификаций на естественном языке через ИИ-чат и
  поддержкой DirectX/OpenGL/WebGL/WebGPU.
- **2026-08-20 (продолжение): зафиксирована концепция «ИИ-недвижимость
  × ИИ-стройка»**, объединяющая `open-cg-cad` и `aruaru-llm` для
  автогенерации 3D-моделей (дома, здания, мосты, туннели и т. д.) по
  данным об участке; позже расширена на маглев-поезда и CAD-модели
  полупроводников (CPU/GPU/NPU), с честной оговоркой о сложности
  охвата архитектуры, гражданского строительства, подвижного состава и
  проектирования полупроводников в одной системе. Только заметка,
  работа не начата.

- **2026-08-08 (продолжение 12): реализована загрузка текстур из реальных
  файлов PNG, проверено на реальном оборудовании Windows + Linux.** Новый
  модуль `png_loader.rs` (используя крейт `png`, версии 0.17.x) реализует
  `load_png_rgba8`, нормализуя изображения RGB/RGBA/оттенки серого/оттенки
  серого+альфа/палитра в RGBA8 (расширение палитры и нормализация
  16-бит→8-бит делегированы собственным трансформациям крейта `png`, а не
  реализованы вручную). Реальный тестовый актив (`assets/sample_sprite.png`,
  шахматная доска 2x2 с одним полупрозрачным квадрантом) был сгенерирован
  и закоммичен. Проверено на реальном оборудовании как Windows
  (NVIDIA GT 730), так и Linux (WSL2 Ubuntu/Mesa llvmpipe): непрозрачные
  квадранты совпадают точно, а полупрозрачный квадрант даёт точно тот
  композитный цвет с альфа-блендингом, который предсказан стандартной
  формулой «over». Весь рабочий набор: `cargo build`/`clippy` чисто (0
  предупреждений); `cargo test --workspace --release` проходит все 33
  теста на реальном оборудовании + 56 юнит-тестов, без регрессий. Честное
  раскрытие: чересстрочные PNG и PNG с 16 битами на канал реально не
  протестированы (полагаемся только на автоматическую обработку крейтом
  `png`); `directx-graphics-window` (демо реального окна) пока не
  вызывает этот загрузчик (по-прежнему текстура сплошного цвета 1x1).

- **2026-08-08 (продолжение 11): реализован альфа-блендинг (полупрозрачные
  спрайты), проверено на реальном оборудовании Windows + Linux.**
  Стандартный альфа-блендинг «over» включён в построении конвейера
  `render_sprites_and_read_back` (`SRC_ALPHA`/`ONE_MINUS_SRC_ALPHA`/`ADD`).
  Поскольку `src.a=1.0` численно эквивалентно `blend_enable=false`, все
  существующие тесты непрозрачных спрайтов подтверждены дающими идентичные
  результаты (неразрушающее, аддитивное изменение). Новый тест проверил
  результат стандартной формулы «over» на реальном оборудовании, обе ОС
  совпадают точно. Честное раскрытие: этот блендинг включён только в
  оффскрин-пути `render_sprites_and_read_back` — `directx-graphics-window`
  (демо реального окна) пока не обновлён под это соответствие; поддержан
  только режим блендинга «over» (без аддитивного/мультипликативного
  режимов); взаимодействие проверки глубины и порядка блендинга не
  проверено (в этом проходе нет буфера глубины, только 2D-спрайты).
