# PORTING.md — что переиспользуемо, кем и как (сокращённая версия)

> **Примечание**: это сокращённый перевод. Полное техническое руководство
> с деталями кода и подводными камнями остаётся доступным только в
> оригинальном [PORTING.md](PORTING.md) — сверяйтесь с ним перед фактическим
> заимствованием паттерна.

Сводка переиспользуемых паттернов реализации из этого проекта, для тех,
кто переносит их в другой проект:

1. **`crates/directx-shader-translate`**: парсер контейнера/чанков DXBC
   (байткод шейдеров D3D9/10/11, SM<=5.1) (`parse_dxbc`), плюс узко
   специализированный транслятор DXBC(SM5.0)→SPIR-V (`translate_shader`)
   именно для тех форм опкодов, которые реально выдаёт `fxc.exe` для
   собственных шейдеров этого проекта: одиночные операции
   (add/mul/sub-через-негированный-add/div), цепочки последовательных
   бинарных операций произвольной длины (на основе дерева регистровых
   выражений, а не хардкодинга по каждой длине — проверено вплоть до 7
   элементов *без единого* изменения в производственном коде на каждое
   новое количество элементов), и граничные варианты (`if (id.x < N)`) тех
   же операций, генерирующие настоящий SPIR-V
   `OpSelectionMerge`/`OpBranchConditional`. Любая другая форма опкода
   честно отклоняется через `SpirvGenError::UnsupportedShader`, а не
   молча транслируется неверно — это **не** общий декодер SM5.0.
2. **Поддержка DXIL (SM6+, D3D12)** (`src/dxil.rs`): `parse_dxil_container`
   обходит сырой битовый поток LLVM (через обобщённый крейт
   `llvm-bitcode`), чтобы разрешить таблицу типов и декодировать
   инструкции функций; семейство функций
   `resolve_vector_add_dxil_calls` дизамбигуирует intrinsic-вызовы
   `dx.op.*` из DXIL (CreateHandle/ThreadId/BufferLoad/BufferStore)
   относительно документированных Microsoft номеров опкодов из DXIL.rst.
   `translate_dxil_..._to_spirv` использует общий эмиттер SPIR-V
   (`emit_spirv_for_kernel`) с бэкендом DXBC, так что оба формата
   контейнера производят SPIR-V через единый путь кода. Размер рабочей
   группы (`numthreads`) реально извлекается из `METADATA_BLOCK` DXIL
   (`dx.entryPoints` → `ShaderProperties`), а не захардкожен. Обобщение
   граничных цепочек (см. выше) было проверено целиком на DXBC и DXIL
   для цепочек длиной вплоть до 7 элементов.
3. **Графический конвейер D3D11**: `translate_vertex_shader`/
   `translate_pixel_shader` генерируют реальный графический SPIR-V для
   фиксированной сквозной пары VS/PS, валидированный двумя независимыми
   способами (повторный разбор rspirv + реальный `spirv-val.exe` из
   Vulkan SDK, оба с кодом выхода 0). Новый крейт
   `crates/directx-graphics-vulkan` добавляет `ash` как собственную
   **прямую** зависимость этого проекта (не поверх `opencuda-vulkan`,
   который был подтверждён аудитом исходников как только для
   диспетчеризации compute) и реализует реальный render pass, framebuffer
   и `VkGraphicsPipelineCreateInfo`. Он рисует и считывает обратно
   треугольники и текстурированные/многоспрайтовые сцены со стандартным
   альфа-блендингом «over» и реальной загрузкой текстур из файлов PNG
   (крейт `png`), всё проверено на реальном оборудовании NVIDIA GT 730
   (Windows) *и* WSL2 Ubuntu/Mesa llvmpipe (Linux), с совпадающими
   результатами на обеих ОС.
4. **`crates/directx-graphics-window`**: реальное окно + реальная
   Vulkan-swapchain + реальный ввод с клавиатуры (winit + ash-window),
   удерживающее собственный независимый экземпляр/устройство Vulkan
   отдельно от оффскрин-контекста `directx-graphics-vulkan` — держите оба
   в синхронизации при использовании обоих (например, альфа-блендинг в
   настоящее время включён только в оффскрин-пути). Произведено
   интерактивное демо в стиле Breakout, подтверждённое работающим
   собственными глазами пользователя (движение весла + отскок мяча).
5. **Соглашение о зависимостях по пути**: этот крейт зависит от
   `opencuda-core`/`opencuda-vulkan` из `open-cuda` через относительные
   зависимости по пути, на один уровень каталога глубже, чем соглашение
   о родственных репозиториях под `F:\runo`, используемое в остальной
   части этой экосистемы (например, `aruaru-llm`, `aruaru-db`) — это
   **зависимости только для разработки (dev-dependencies)**, у самой
   опубликованной библиотеки нет зависимости от `open-cuda`.
6. **Замечание об охвате: античит на уровне ядра**: для тех, кто переносит
   этот проект к цели «запускать реальные Windows-игры на Linux» —
   античит на уровне ядра (Riot Vanguard, BattlEye в режиме ядра и т. д.)
   блокирует Linux/Proton-подобные окружения по замыслу, независимо от
   того, насколько полным станет этот слой трансляции шейдеров. Это не
   дефект для исправления; тайтлы, использующие такой античит, находятся
   вне досягаемости этого проекта независимо от полноты трансляции.

## Что ещё НЕ переиспользуемо (честные пробелы)

- Нет общего декодера инструкций SM5.0 или SM6.0 — обрабатываются только
  конкретные классы форм/опкодов, описанные выше; всё остальное честно
  отклоняется, а не транслируется неверно.
- Более высокие уровни D3D12 (списки команд, кучи дескрипторов, корневые
  сигнатуры) полностью не реализованы.
- Нет буфера глубины, нет проверки интерполяции по-разному окрашенных
  вершин за пределами случая градиентного треугольника, и оборудование GPU
  AMD/Intel, а также нативное выполнение на настольных Linux/macOS остаются
  непроверенными (пути кода для обнаружения PCI vendor ID AMD/Intel
  существуют, но никогда не запускались на реальном оборудовании AMD/Intel
  в этом окружении разработки).
