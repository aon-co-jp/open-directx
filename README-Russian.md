Кроссплатформенный слой совместимости DirectX (D3D9/10/11/12) — в духе
DXVK / vkd3d-proton — цель которого запускать немодифицированные Windows
DirectX-приложения на Linux (а в перспективе на Android/macOS) путём
трансляции байткода шейдеров DXBC/DXIL в SPIR-V и диспетчеризации через
существующий Vulkan-бэкенд вычислений
([open-cuda](https://github.com/aon-co-jp/open-cuda)'s `opencuda-vulkan`).

Полное технико-экономическое обоснование, честный охват/дорожную карту и
журнал HANDOFF по сессиям см. в [`CLAUDE.md`](CLAUDE.md) — этот README
лишь резюмирует текущее, проверенное состояние.

### Матрица поддержки платформ и вендоров (добавлено 2026-07-27, честное раскрытие)

Сам по себе DirectX — API только для Windows/Xbox — «кроссплатформенность»
здесь означает, что байткод DXBC/DXIL транслируется в SPIR-V и
диспетчеризуется через Vulkan, который и есть то, что фактически доходит
до платформ, отличных от Windows. В коде самого репозитория сегодня нет
никакого `cfg(windows)` или другого gate по платформе (парсер DXBC,
кодогенерация SPIR-V и `directx-graphics-vulkan` — всё это обычный,
платформенно-нейтральный Rust + `ash`), поэтому переносимость сборки/тестов
следует за досягаемостью самого Vulkan:

| Платформа | Путь | Статус |
|---|---|---|
| Windows | нативный Vulkan | **Проверено на реальном оборудовании** (машина разработки этого репозитория, NVIDIA GeForce GT 730) |
| Linux | нативный Vulkan | Должно собираться/запускаться без изменений (нет кода, специфичного для Windows, который бы это блокировал) — **пока не протестировано на реальной машине Linux в этом окружении** |
| Android | нативный Vulkan | `open-cuda` подтвердил, что кросс-компиляция под `aarch64-linux-android` успешна (согласно его CLAUDE.md); выполнение на реальном устройстве (`vkCreateInstance` на реальном телефоне) пока не выполнено |
| macOS | Vulkan через [MoltenVK](https://github.com/KhronosGroup/MoltenVK) (транслирует в Metal) | Пока не пробовалось — MoltenVK это слой трансляции, а не нативный Vulkan, поэтому это более слабая гарантия, чем Linux/Android |
| iOS / iPadOS (добавлено 2026-08-17) | Vulkan через MoltenVK (транслирует в Metal) | Пока не пробовалось. **К macOS и здесь применима та же оговорка про MoltenVK** — Vulkan не работает нативно на iOS/iPadOS, только через этот слой трансляции, поэтому паритет с путём Windows/Vulkan-native не гарантирован, пока не опробовано на реальном устройстве. Также требует Apple Developer Program для официального распространения. |
| Различные UNIX/BSD (добавлено 2026-08-17) | нативный Vulkan, вероятно | Не исследовано — поддержка Vulkan варьируется по дистрибутиву/драйверу; ожидается переиспользование большей части пути Linux после исследования |
| Sony PlayStation 4/5/6/7 | н/д | Явно вне охвата на данный момент — см. примечание «Целевые платформы семейства PlayStation» ниже и `CLAUDE.md` |
| Nintendo Switch 2 / 3 (добавлено 2026-08-17) | н/д | Тот же статус «будущая амбиция, отложено до официального SDK/NDA», что и у PlayStation. **Switch 3 официально не анонсирован Nintendo по состоянию на 2026-08-17 — его упоминание здесь лишь заполнитель на случай если/когда он будет анонсирован, а не основано на реальной информации о продукте.** |

Покрытие вендоров GPU (сопоставление по PCI vendor ID, согласовано между
этим репозиторием и `open-cuda`: NVIDIA `0x10DE`, AMD `0x1002`/`0x1022`,
Intel `0x8086`):

| Вендор | Статус |
|---|---|
| NVIDIA | **Проверено на реальном оборудовании** (GeForce GT 730) |
| AMD | Код сопоставления vendor ID существует и проходит проверку типов, но **никогда не запускался на реальном оборудовании AMD** в этом окружении — считать непроверенным |
| Intel | То же, что и AMD: код существует, **никогда не проверялся на реальном оборудовании Intel GPU** |

Не требуется никакого исправления, чтобы сделать эти три vendor ID
*обнаруживаемыми* — код уже корректен и идентичен во всех
`open-directx`/`opencuda-vulkan`/`opencuda-directx`. Чего не хватает —
реального оборудования AMD/Intel для фактической проверки этого пути
кода, которого у данного окружения разработки нет.

## Текущее состояние (2026-07-27, последнее: градиентная интерполяция, диагностика вендора GPU, sub/div в цепочке)

Три инкремента добавлены поверх минимального графического конвейера D3D11
и работы над классом цепочек DXBC ниже, все проверены на реальной NVIDIA
GT 730 этой машины: (1) `render_gradient_triangle_and_read_back` —
графический конвейер теперь может присваивать отдельный цвет каждой
вершине (не только вырожденный случай единого цвета), проверено через
проверку инварианта разбиения единицы на пикселях, считанных с реального
оборудования. (2) `enumerate_graphics_devices()` — закрывает разрыв
диагностического паритета, где у `open-cuda` в пути Compute было
обнаружение vendor ID, а в пути Graphics здесь — нет; самостоятельно, без
новой зависимости от `opencuda-vulkan`. (3) `decode_chain_shape` теперь
поддерживает `sub`/`div` (ранее явно отклонялись как непроверяемые) — новый
шейдер (`vector_sub_div_chain.hlsl`) был реально скомпилирован `fxc.exe`, и
его дамп SHEX использован для подтверждения точного порядка операндов,
затем проверен целиком относительно CPU-эталона на реальном оборудовании.
Полный отчёт см. в HANDOFF `CLAUDE.md` (записи 2026-07-27).

## Текущее состояние (2026-07-25, последнее: вертикальный срез DXIL завершён на реальном оборудовании)

Вертикальный срез вычислительного шейдера D3D12/DXIL теперь достигает
полного паритета с D3D11/DXBC: `vector_add.dxil` (реальный вывод
`dxc.exe -T cs_6_0`) декодируется целиком (контейнер -> битовый поток LLVM
-> таблица типов -> инструкции -> все 7 записей `Call` дизамбигуированы до
реального смысла `dx.op.*`) и транслируется в реальный SPIR-V
(`directx_shader_translate::translate_dxil_vector_add_to_spirv`), который
`tests/vector_add_dxil_real_vulkan.rs` диспетчеризует на реальной NVIDIA
GT 730 этой машины и проверяет численное совпадение с CPU-эталоном
`a[i]+b[i]`. Это по-прежнему лишь одна известная форма шейдера, а не общий
декодер SM6.0 — точную границу см. в разделе «Не реализовано (честный
охват)» ниже. Размер рабочей группы SPIR-V теперь по-настоящему извлекается
из `METADATA_BLOCK` DXIL (`dx.entryPoints` -> `ShaderProperties` ->
`NumThreads`), а не захардкожен — полный отчёт см. в записи HANDOFF
2026-07-25 «продолжение 9» в `CLAUDE.md`, а «продолжение 7» — по
изначальному достижению вертикального среза, разрыв в котором это закрыло.

## Текущее состояние (2026-07-25, продолжение: парсинг DXIL на уровне битового потока + парсинг DXBC для VS/PS D3D11)

Две новые части работы добавлены поверх вертикального среза вычислительного
шейдера Phase 1 ниже:

- **DXIL (D3D12/SM6+) — реальные байты разобраны, только на уровне
  контейнера/битового потока.** `crates/directx-shader-translate/src/dxil.rs`
  (`parse_dxil_container`) парсит реальный контейнер DXBC, скомпилированный
  `dxc.exe -T cs_6_0` (`shaders/vector_add_dxil.hlsl` ->
  `shaders/vector_add.dxil`, произведён `tools/compile-dxbc-shaders.ps1`):
  извлекает `DxilProgramHeader`/`DxilBitcodeHeader` чанка `DXIL` (вид
  шейдера, SM6.0, версия DXIL) через существующий крейт `dxbc`, затем
  передаёт сырую полезную нагрузку LLVM bitcode крейту `llvm-bitcode`
  (новая добавленная зависимость, обобщённый ридер битового потока LLVM без
  знания специфики DXIL), чтобы реально декодировать дерево блоков/записей.
  Подтверждено на реальных байтах: маска-обёртка LLVM `BC\xC0\xDE`, один
  верхнеуровневый `MODULE_BLOCK` (id 8), и стандартные субблоки LLVM внутри
  него — `TYPE_BLOCK_ID_NEW`(17), `PARAMATTR_GROUP_BLOCK`(10),
  `PARAMATTR_BLOCK`(9), `CONSTANTS_BLOCK`(11), `FUNCTION_BLOCK`(12, x5 — по
  одному на базовый блок `main`), `VALUE_SYMTAB_BLOCK`(14),
  `METADATA_BLOCK`(15, x2). **Обновление (2026-07-25, продолжение, трек
  D3D12)**: с тех пор добавлено разрешение таблицы типов и грубое
  декодирование инструкций (`resolve_type_table`/`decode_function_
  instructions` в том же файле), применяя документированные LLVM таблицы
  записей `TYPE_BLOCK`/`FUNC_CODE` к реальным байтам `vector_add.dxil` —
  подтверждена таблица типов из 22 записей, включая `Float` и
  `StructNamed{"class.RWStructuredBuffer<float>"}`, и реальная
  последовательность инструкций (`DeclareBlocks -> Call*5 -> ExtractValue ->
  Call -> ExtractValue -> BinOp -> Call -> Ret`). **Обновление (2026-07-25,
  продолжение 6)**: все 7 записей `Call` теперь дизамбигуированы.
  `resolve_vector_add_dxil_calls` разрешает имена функций
  `VALUE_SYMTAB_BLOCK` (найденные через `Record::take_payload()`, а не
  `fields()` — реальный пробел в понимании крейта в предыдущей записи) и
  вручную декодирует относительное кодирование операндов LLVM (проверено
  вручную по реальным байтам), давая
  `[CreateHandle{range_id:2}, CreateHandle{range_id:1},
  CreateHandle{range_id:0}, ThreadId, BufferLoad{handle_range_id:0},
  BufferLoad{handle_range_id:1}, BufferStore{handle_range_id:2}]`. Номера
  опкодов DXIL (`CreateHandle`=57, `BufferLoad`=68, `BufferStore`=69,
  `ThreadId`=93) подтверждены через веб-поиск в `DirectXShaderCompiler/
  docs/DXIL.rst` Microsoft, а не приняты на веру по памяти, и точно
  совпали с реально декодированными константами. **По-прежнему нет
  трансляции DXIL-в-SPIR-V** — это следующий инкремент. См. «Не
  реализовано» ниже.
- **Графический конвейер D3D11 — реальная генерация SPIR-V для VS/PS
  достигнута и валидирована, растеризатора/draw пока нет.**
  `shaders/triangle_vs.hlsl`/`shaders/triangle_ps.hlsl` (минимальная пара
  сквозных вершинного+пиксельного шейдеров, вход `POSITION`/`COLOR`, выход
  `SV_POSITION`/`SV_TARGET`) скомпилирована реальным `fxc.exe /T vs_5_0`/
  `/T ps_5_0`. `parse_dxbc` разбирает оба без изменений.
  `spirv_gen::translate_vertex_shader`/`translate_pixel_shader` (новые)
  декодируют реальную, фиксированную последовательность опкодов SHEX
  (`dcl_input`x2/`dcl_output_siv`/`dcl_output`/`mov`x3/`ret` для VS;
  `dcl_input_ps`(linear)/`dcl_output`/`mov`/`ret` для PS) и генерируют
  реальный графический SPIR-V: `OpEntryPoint Vertex`/`Fragment` (не
  `GLCompute`), переменные класса хранения `Input`/`Output` с декорациями
  `Location`, `BuiltIn Position` на выходе `SV_POSITION` вершинного
  шейдера, и `OpExecutionMode ... OriginUpperLeft` на фрагментном шейдере.
  Валидировано двумя способами: (1) собственный загрузчик `rspirv`
  повторно разбирает сгенерированные байты без ошибок, (2) реальный
  `spirv-val.exe` из Vulkan SDK
  (`C:\VulkanSDK\1.4.350.0\Bin\spirv-val.exe`) был запущен на обоих
  сгенерированных модулях и вернул код выхода 0 без диагностики для обоих.
  `translate_shader`/`translate_chain_shader` (только Compute) по-прежнему
  корректно отклоняют оба шейдера. **Растеризатора, фреймбуфера, реального
  вызова отрисовки Vulkan не существует** — было подтверждено (чтением
  реального исходного кода) что `opencuda-vulkan` вообще не имеет кода
  `VkGraphicsPipelineCreateInfo`/render pass/framebuffer, только
  Compute-диспетчеризация, поэтому реально отрисованный пиксель вне охвата
  этого прохода. Честную границу вехи см. в HANDOFF `CLAUDE.md`.

## Текущее состояние (2026-07-26, достигнута веха минимального графического конвейера D3D11)

Новый крейт `crates/directx-graphics-vulkan` добавляет `ash` как
**прямую** зависимость этого рабочего пространства (не поверх
`opencuda-vulkan`, который был подтверждён аудитом исходников как
Compute-only). Он реализует реальный render pass, framebuffer и
`VkGraphicsPipelineCreateInfo`, повторно используя уже сгенерированный,
уже прошедший `spirv-val` SPIR-V из `translate_vertex_shader`/
`translate_pixel_shader` выше (трансляция шейдера не реализуется заново).
`render_uniform_triangle_and_read_back` рисует один «большой треугольник»
на весь viewport с единым равномерным цветом вершин, считывает
отрисованное изображение через видимый хосту staging-буфер, и тест на
реальном оборудовании
(`crates/directx-graphics-vulkan/tests/triangle_real_vulkan.rs`) проверяет,
что каждый считанный пиксель совпадает со сквозным цветом вершины на
реальной NVIDIA GT 730, присутствующей на этой машине (`cargo test -p
directx-graphics-vulkan --test triangle_real_vulkan -- --nocapture`: 1
passed). Охват намеренно узкий: одна фиксированная пара шейдеров, один
вызов отрисовки, без буфера глубины/текстур/swapchain/проверки
интерполяции нескольких треугольников. Полный честный отчёт см. в HANDOFF
`CLAUDE.md` (продолжение 2026-07-26).

## Текущее состояние (2026-07-25, вертикальный срез Phase 1 обобщён до 3 известных шейдеров)

`crates/directx-shader-translate` теперь выполняет полный вертикальный
срез для **трёх конкретных известных шейдеров** (`vector_add.hlsl`,
`vector_mul.hlsl`, `vector_sub_bounded.hlsl`): парсинг DXBC -> декодирование
узкого подмножества опкодов SM5.0 -> кодогенерация SPIR-V (через `rspirv`)
-> реальная диспетчеризация Vulkan (`opencuda-vulkan` от `open-cuda`) ->
численное совпадение с CPU-эталоном, проверено на реальной NVIDIA GT 730
этой машины. **Это по-прежнему не общий декодер SM5.0-в-SPIR-V** — см.
«Не реализовано» ниже.

- `parse_dxbc` (Phase 0): интроспекция контейнера/чанков DXBC (наличие
  RDEF/ISGN/OSGN/SHEX), без изменений относительно исходного фронтенда.
- `spirv_gen::translate_shader` (Phase 1, обобщён 2026-07-25): распознаёт
  3 формы опкодов, реально выдаваемые `fxc.exe`, все имеющие общий скелет
  (`dcl_globalFlags` -> опционально `dcl_constantbuffer` -> 3x
  `dcl_uav_structured` -> `dcl_input` -> `dcl_temps` -> `dcl_thread_group`
  -> опционально `ult`+`if` -> 2x `ld_structured` -> `add`/`mul` ->
  `store_structured` -> опционально `endif` -> `ret`):
  - `vector_add.hlsl`: `add`, без граничной проверки.
  - `vector_mul.hlsl`: `mul` вместо `add`.
  - `vector_sub_bounded.hlsl`: `add` с флагом `negate` на первом операнде
    источника (подтверждено дампом реального вывода `fxc.exe` — `fxc`
    оптимизирует `a - b` в `add dest, -b, a`, а не выдаёт выделенный
    опкод `sub`), плюс реальная граничная проверка `if (id.x < N)`
    (`ult` относительно константного буфера + `if`/`endif`), которую
    сгенерированный SPIR-V реализует настоящим
    `OpSelectionMerge`/`OpBranchConditional`, используя push-константу `n`
    для сравнения.
  Любой другой опкод/форма отклоняется через `SpirvGenError::
  UnsupportedShader`, а не молча оттранслируется неверно. Точки привязки
  UAV, размер группы потоков, оператор и наличие граничной проверки — всё
  извлекается из реально разобранного DXBC, а не захардкожено.
  `translate_vector_add_shader` сохранён как тонкий обратно совместимый
  алиас для `translate_shader`.
- `tests/vector_add_real_vulkan.rs`, `tests/vector_mul_real_vulkan.rs`,
  `tests/vector_sub_bounded_real_vulkan.rs`: каждый диспетчеризует свой
  оттранслированный SPIR-V через реальный `opencuda-vulkan::VulkanDevice`
  (`ash`, фича `real-vulkan`) от `open-cuda` и проверяет вывод GPU против
  CPU-эталона для 256 элементов (эпсилон 1e-3/1e-2). Тест граничной проверки
  дополнительно диспетчеризует 320 потоков с логическим количеством
  элементов 256 и проверяет, что элементы 256..320 никогда не записываются
  (остаются на значении-часовом), доказывая, что ветвь `if (id.x < N)` в
  сгенерированном SPIR-V действительно управляет выполнением, а не просто
  компилируется.
- `examples/dump_shex.rs`: небольшой самостоятельный инструмент (`cargo run
  -p directx-shader-translate --example dump_shex -- <path.dxbc>`),
  использованный в этой сессии для проверки реальных потоков опкодов SHEX
  перед написанием поддержки декодера для них; оставлен для будущей
  пооперационной работы по обобщению.

**С момента написания заголовка этого раздела** добавлен 4-й
однооперационный шейдер (`vector_div.hlsl`, чистый `div`) в
`translate_shader` по тому же паттерну, а — совсем недавно — по-настоящему
другой класс паттерна, `spirv_gen::translate_chain_shader`, был добавлен
рядом с ним (не заменяя его): он декодирует реальное дерево регистровых
выражений последовательных бинарных операций (add/mul, без управления
потоком) вместо одной фиксированной операции, проверено на заново
скомпилированном шейдере, чей реальный SHEX оказался переиспользующим
компоненты одного временного регистра через CSE fxc, а не объявляющим
дополнительные временные. Полный, актуальный отчёт см. в записи HANDOFF
2026-07-25 «продолжение 9» в `CLAUDE.md` (этот раздел оставлен как
изначально написанный для исторической точности о состоянии на середину
дня 2026-07-25).

## Не реализовано (честный охват)

- **Общее декодирование инструкций SM5.0.** Обрабатываются только 3 формы
  опкодов выше; любой другой вычислительный шейдер D3D11 (иная раскладка
  ресурсов, другое управление потоком, другие intrinsics, более одной
  граничной проверки, `div`/`sub` как реальный опкод вместо
  негированного `add` и т.д.) отклоняется, а не оттранслируется неверно.
  Построение реального общего декодера (или адаптация/перенос
  существующего, например, более пристальное изучение подхода
  `dxbc-spirv`/`dxil-spirv`) остаётся фактической следующей вехой.
- **DXIL (Shader Model 6+, D3D12): вертикальный срез `vector_add.dxil`
  теперь завершён целиком, на реальном оборудовании — но по-прежнему
  только для этой одной известной формы шейдера, а не общего SM6.0.**
  `resolve_type_table`/`decode_function_instructions`/
  `resolve_vector_add_dxil_calls` в `dxil.rs` декодируют реальные записи
  `TYPE_BLOCK`/`FUNCTION_BLOCK`/`VALUE_SYMTAB_BLOCK` относительно
  документированных кодов LLVM и дизамбигуируют все 7 записей `Call` до
  их реального смысла `dx.op.*` (`CreateHandle`/`ThreadId`/`BufferLoad`/
  `BufferStore`, с точками привязки UAV). `translate_dxil_vector_add_to_spirv`
  (новое) подаёт этот разрешённый вывод в общий `emit_spirv_for_kernel`
  из `spirv_gen.rs` (выделенный из `emit_spirv` пути DXBC, чтобы оба
  бэкенда генерировали из одного пути кода) для производства реального
  SPIR-V, который `tests/vector_add_dxil_real_vulkan.rs` диспетчеризует
  на реальной NVIDIA GT 730 этой машины через `opencuda-vulkan` и
  проверяет совпадение с CPU-эталоном `a[i]+b[i]` для всех 256
  элементов — та же строгость, что и у DXBC-теста `vector_add`. **Размер
  рабочей группы теперь реально извлекается, а не захардкожен**:
  `extract_numthreads_from_metadata` (`dxil.rs`) проходит реальный путь
  `METADATA_BLOCK` `dx.entryPoints` -> кортеж по entry point ->
  `ShaderProperties` -> `kDxilNumThreadsTag` (=4, подтверждено по
  исходникам `DxilMetadataHelper.h`/`.cpp` из
  `DirectXShaderCompiler` Microsoft) и разрешает узел `{x,y,z}`
  относительно реального списка значений модуля, давая `(64,1,1)` из
  реальных байтов `vector_add.dxil` — известный хардкод из предыдущей
  записи закрыт, а синтетический регрессионный тест доказывает, что
  логика извлечения возвращает *другое* значение при других метаданных
  (а не просто «всегда возвращает 64,1,1 несмотря ни на что»). Любая
  другая форма опкода/операнда (другая операция, несколько базовых
  блоков, граничные проверки) по-прежнему отклоняется, а не
  оттранслируется неверно. Поддержка списка команд/кучи дескрипторов/
  корневой сигнатуры D3D12 (слой над трансляцией шейдеров) не затронута.
- **Декодер DXBC обобщён за пределы 4 фиксированных однооперационных
  форм: теперь обрабатывает цепочки последовательных бинарных операций
  (без управления потоком) через реальное дерево регистровых выражений,
  а не через 5-ю захардкоженную форму.** `spirv_gen::translate_chain_
  shader`/`decode_chain_shape` обходят `ld_structured`/`add`/`mul`/
  `store_structured` и строят реальное дерево выражений, ключом к
  которому служит (временный регистр, компонент), поэтому обрабатывает
  1 операцию, 2 операции или N операций одинаково — проверено на заново
  скомпилированном реальном шейдере (`vector_add_mul_chain.hlsl`,
  `t = A[i]+B[i]; Out[i] = t*A[i]`), чей реальный SHEX оказался
  переиспользующим компоненты `.x`/`.y` одного временного регистра (fxc
  выполнил CSE повторной загрузки `A[i]` вместо повторной выдачи
  `ld_structured`) — подлинное, непредсказанное открытие, которое
  декодер на основе дерева обрабатывает без дополнительных случаев.
  Диспетчеризовано и проверено на реальной NVIDIA GT 730 против
  CPU-эталона `(a[i]+b[i])*a[i]`. `sub`/`div` внутри цепочки намеренно
  по-прежнему отклоняются (их семантика порядка операндов была проверена
  только для одиночного случая). Исходные 4 однооперационные формы не
  затронуты и по-прежнему проходят без изменений.
- **Графический конвейер D3D11: подтверждён рабочий парсинг контейнера
  DXBC для VS/PS, но нет кодогенерации SPIR-V, нет растеризатора, нет
  реально отрисованного на экране треугольника.** Полный конвейер
  (растеризатор, сэмплирование текстур, состояние блендинга,
  output-merger) остаётся вне охвата; так же как и расширение узкого
  декодера форм опкодов `spirv_gen` для понимания `dcl_output_siv`/
  `dcl_input_ps`/режимов интерполяции.
- Целевые платформы семейства PlayStation — явно вне охвата; юридическое/
  ToS-обоснование см. в `CLAUDE.md`.
