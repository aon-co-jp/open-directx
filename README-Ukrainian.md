Кросплатформовий шар сумісності DirectX (D3D9/10/11/12) — у дусі
DXVK / vkd3d-proton — метою якого є запуск немодифікованих застосунків
Windows DirectX на Linux (а згодом і Android/macOS) шляхом трансляції
байткоду шейдерів DXBC/DXIL у SPIR-V та диспетчеризації через наявний
Vulkan-бекенд для обчислень ([open-cuda](https://github.com/aon-co-jp/open-cuda)'s
`opencuda-vulkan`).

Див. [`CLAUDE.md`](CLAUDE.md) щодо повного обґрунтування дизайну, чесного
обсягу/дорожньої карти та журналу HANDOFF сесій — цей README лише
підсумовує поточний, перевірений стан.

### Матриця підтримки платформ і виробників (додано 2026-07-27, чесне розкриття)

Сам DirectX — це API лише для Windows/Xbox — «кросплатформовість» тут
означає, що байткод DXBC/DXIL транслюється в SPIR-V і диспетчеризується
через Vulkan, який і фактично досягає платформ, відмінних від Windows.
Наразі в коді цього репозиторію немає жодного `cfg(windows)` чи іншого
платформо-специфічного гейтингу (парсер DXBC, кодогенератор SPIR-V та
`directx-graphics-vulkan` — усе це звичайний, платформо-нейтральний Rust +
`ash`), тому портованість збірки/тестування слідує за досяжністю самого
Vulkan:

| Платформа | Шлях | Статус |
|---|---|---|
| Windows | нативний Vulkan | **Перевірено на реальному обладнанні** (машина розробки цього репозиторію, NVIDIA GeForce GT 730) |
| Linux | нативний Vulkan | Має збиратися/працювати без змін (немає коду, специфічного для Windows, що це блокує) — **ще не перевірено на реальній машині Linux у цьому середовищі** |
| Android | нативний Vulkan | `open-cuda` перевірив, що крос-компіляція `aarch64-linux-android` вдається (згідно з його CLAUDE.md); виконання на реальному пристрої (`vkCreateInstance` на реальному телефоні) досі очікує на перевірку |
| macOS | Vulkan через [MoltenVK](https://github.com/KhronosGroup/MoltenVK) (транслює у Metal) | Ще не пробували — MoltenVK це шар трансляції, а не нативний Vulkan, тож це слабша гарантія, ніж Linux/Android |
| iOS / iPadOS (додано 2026-08-17) | Vulkan через MoltenVK (транслює у Metal) | Ще не пробували. **До macOS застосовується той самий застереження щодо MoltenVK** — Vulkan не працює нативно на iOS/iPadOS, лише через цей шар трансляції, тож паритет із шляхом Windows/Vulkan-native не гарантований, доки не буде фактично випробувано на пристрої. Також вимагає Apple Developer Program для офіційного поширення. |
| Різні системи UNIX/BSD (додано 2026-08-17) | нативний Vulkan, ймовірно | Не досліджено — підтримка Vulkan різниться залежно від дистрибутива/драйвера; очікується перевикористання більшості шляху Linux після дослідження |
| Sony PlayStation 4/5/6/7 | н/д | Явно поза межами наразі — див. примітку «Цілі родини PlayStation» нижче та `CLAUDE.md` |
| Nintendo Switch 2 / 3 (додано 2026-08-17) | н/д | Такий самий статус «майбутня амбіція, відкладено до офіційного SDK/NDA», що і PlayStation. **Switch 3 офіційно не анонсовано Nintendo станом на 2026-08-17 — його включення тут є лише заповнювачем на випадок, якщо/коли його анонсують, а не базується на реальній інформації про продукт.** |

Покриття виробників GPU (зіставлення за PCI vendor ID, узгоджене між цим
репозиторієм та `open-cuda`: NVIDIA `0x10DE`, AMD `0x1002`/`0x1022`,
Intel `0x8086`):

| Виробник | Статус |
|---|---|
| NVIDIA | **Перевірено на реальному обладнанні** (GeForce GT 730) |
| AMD | Код зіставлення vendor ID існує та проходить перевірку типів, але **ніколи не запускався на реальному обладнанні AMD** у цьому середовищі — вважати неперевіреним |
| Intel | Так само, як AMD: код існує, **ніколи не перевірявся на реальному обладнанні GPU Intel** |

Жодного виправлення не потрібно, щоб зробити ці три vendor ID
*виявлюваними* — код вже правильний та ідентичний у `open-directx`/
`opencuda-vulkan`/`opencuda-directx`. Чого бракує — це реального
обладнання AMD/Intel для фактичного виконання цього шляху коду, якого
це середовище розробки не має.

## Поточний стан (2026-07-27, останнє: градієнтна інтерполяція, діагностика виробника GPU, ланцюжок з sub/div)

Три інкременти додано поверх мінімального графічного конвеєра D3D11 та
роботи над класом ланцюжків DXBC нижче, усі перевірено на реальному
NVIDIA GT 730 цієї машини: (1) `render_gradient_triangle_and_read_back`
— графічний конвеєр тепер може призначати окремий колір кожній вершині
(не лише вироджений випадок рівномірного кольору), перевірено через
перевірку інваріанта розбиття одиниці на реальних пікселях зчитування
з обладнання. (2) `enumerate_graphics_devices()` — усуває розрив
діагностичного паритету, де шлях Compute `open-cuda` мав виявлення
vendor ID, а шлях Graphics тут — ні; самостійний, без нової залежності
від `opencuda-vulkan`. (3) `decode_chain_shape` тепер підтримує `sub`/
`div` (раніше явно відхилялося як неперевірене) — новий шейдер
(`vector_sub_div_chain.hlsl`) фактично скомпільовано через `fxc.exe`, а
його дамп SHEX використано для підтвердження точного порядку операндів,
після чого перевірено наскрізно проти еталонної реалізації CPU на
реальному обладнанні. Див. HANDOFF у `CLAUDE.md` (записи 2026-07-27) для
повного опису.

## Поточний стан (2026-07-25, останнє: вертикальний зріз DXIL завершено на реальному обладнанні)

Вертикальний зріз обчислювальних шейдерів D3D12/DXIL тепер досягає
повного паритету з D3D11/DXBC: `vector_add.dxil` (реальний вивід
`dxc.exe -T cs_6_0`) декодується наскрізно (контейнер -> бітстрім LLVM
-> таблиця типів -> інструкції -> усі 7 записів `Call` розшифровано до
реального значення `dx.op.*`) і транслюється в реальний SPIR-V
(`directx_shader_translate::translate_dxil_vector_add_to_spirv`), який
`tests/vector_add_dxil_real_vulkan.rs` диспетчеризує на реальному
NVIDIA GT 730 цієї машини та перевіряє числову відповідність еталонній
реалізації CPU `a[i]+b[i]`. Це все ще лише одна відома форма шейдера,
а не загальний декодер SM6.0 — див. «Не реалізовано (чесний обсяг)»
нижче щодо точної межі. Розмір робочої групи SPIR-V тепер справді
видобувається з `METADATA_BLOCK` DXIL (`dx.entryPoints` ->
`ShaderProperties` -> `NumThreads`), а не жорстко закодований — див.
запис HANDOFF «продовження 9» від 2026-07-25 у `CLAUDE.md` для повного
опису, та «продовження 7» щодо оригінального досягнення вертикального
зрізу, розрив у якому це закрило.

## Поточний стан (2026-07-25, продовження: розбір DXIL на рівні бітстріму + розбір DXBC для D3D11 VS/PS)

Дві нові частини роботи додано поверх вертикального зрізу Фази 1
обчислювальних шейдерів нижче:

- **DXIL (D3D12/SM6+) — реальні байти розібрано, лише на рівні
  контейнера/бітстріму.** `crates/directx-shader-translate/src/dxil.rs`
  (`parse_dxil_container`) розбирає реальний контейнер DXBC,
  скомпільований `dxc.exe -T cs_6_0` (`shaders/vector_add_dxil.hlsl` ->
  `shaders/vector_add.dxil`, вироблений `tools/compile-dxbc-shaders.ps1`):
  видобуває `DxilProgramHeader`/`DxilBitcodeHeader` чанка `DXIL` (тип
  шейдера, SM6.0, версія DXIL) через наявний крейт `dxbc`, потім передає
  сирий пейлоад LLVM bitcode крейту `llvm-bitcode` (нова додана
  залежність, загальний зчитувач бітстріму LLVM без специфічних для DXIL
  знань), щоб фактично декодувати дерево блоків/записів. Підтверджено на
  реальних байтах: магія обгортки LLVM `BC\xC0\xDE`, єдиний
  верхньорівневий `MODULE_BLOCK` (id 8), і стандартні підблоки LLVM
  всередині нього — `TYPE_BLOCK_ID_NEW`(17), `PARAMATTR_GROUP_BLOCK`(10),
  `PARAMATTR_BLOCK`(9), `CONSTANTS_BLOCK`(11), `FUNCTION_BLOCK`(12, x5 —
  по одному на базовий блок `main`), `VALUE_SYMTAB_BLOCK`(14),
  `METADATA_BLOCK`(15, x2). **Оновлення (2026-07-25, продовження, напрям
  D3D12)**: відтоді додано розв'язання таблиці типів та грубе декодування
  інструкцій (`resolve_type_table`/`decode_function_instructions` у тому
  ж файлі), застосовуючи задокументовані таблиці записів
  `TYPE_BLOCK`/`FUNC_CODE` LLVM до реальних байтів `vector_add.dxil` —
  підтверджено таблицю з 22 записів, включно з `Float` та
  `StructNamed{"class.RWStructuredBuffer<float>"}`, і реальну
  послідовність інструкцій (`DeclareBlocks -> Call*5 -> ExtractValue -> Call
  -> ExtractValue -> BinOp -> Call -> Ret`). **Оновлення (2026-07-25,
  продовження 6)**: усі 7 записів `Call` тепер розшифровано.
  `resolve_vector_add_dxil_calls` розв'язує імена функцій
  `VALUE_SYMTAB_BLOCK` (знайдені через `Record::take_payload()`, а не
  `fields()` — реальний пробіл у розумінні крейту в попередньому записі)
  і вручну декодує кодування відносних значень-операндів LLVM (перевірено
  вручну проти реальних байтів), даючи `[CreateHandle{range_id:2},
  CreateHandle{range_id:1}, CreateHandle{range_id:0}, ThreadId,
  BufferLoad{handle_range_id:0}, BufferLoad{handle_range_id:1},
  BufferStore{handle_range_id:2}]`. Номери опкодів DXIL
  (`CreateHandle`=57, `BufferLoad`=68, `BufferStore`=69, `ThreadId`=93)
  підтверджено через веб-пошук проти `DirectXShaderCompiler/docs/DXIL.rst`
  Microsoft, а не припущено з пам'яті, і точно збіглися з реальними
  декодованими константами. **Досі немає трансляції DXIL у SPIR-V** — це
  наступний інкремент. Див. «Не реалізовано» нижче.
- **Графічний конвеєр D3D11 — реальна генерація SPIR-V для VS/PS
  досягнута та перевірена, растеризатора/малювання ще немає.**
  `shaders/triangle_vs.hlsl`/`shaders/triangle_ps.hlsl` (мінімальна пара
  прохідних вершинного+піксельного шейдерів, `POSITION`/`COLOR` на вході,
  `SV_POSITION`/`SV_TARGET` на виході) скомпільовано реальним
  `fxc.exe /T vs_5_0`/`/T ps_5_0`. `parse_dxbc` розбирає обидва без
  модифікацій. `spirv_gen::translate_vertex_shader`/
  `translate_pixel_shader` (нові) декодують реальну, фіксовану
  послідовність опкодів SHEX (`dcl_input`x2/`dcl_output_siv`/
  `dcl_output`/`mov`x3/`ret` для VS; `dcl_input_ps`(linear)/`dcl_output`/
  `mov`/`ret` для PS) і випромінюють реальний графічний SPIR-V:
  `OpEntryPoint Vertex`/`Fragment` (не `GLCompute`), змінні класу
  сховища `Input`/`Output` з декораціями `Location`, `BuiltIn Position`
  на виході `SV_POSITION` вершинного шейдера, і
  `OpExecutionMode ... OriginUpperLeft` на фрагментному шейдері.
  Перевірено двома способами: (1) власний завантажувач `rspirv` повторно
  розбирає випромінені байти без помилки, (2) реальний `spirv-val.exe`
  Vulkan SDK (`C:\VulkanSDK\1.4.350.0\Bin\spirv-val.exe`) запущено проти
  обох випромінених модулів і повернуто код виходу 0 без діагностики для
  обох. `translate_shader`/`translate_chain_shader` (лише обчислення)
  досі коректно відхиляють обидва шейдери. **Растеризатора, буфера
  кадру, реального виклику малювання Vulkan не існує** — підтверджено
  (шляхом читання реального джерела), що `opencuda-vulkan` взагалі не
  має коду `VkGraphicsPipelineCreateInfo`/render-pass/framebuffer, лише
  диспетчеризація обчислень, тож фактично відрендерений піксель поза
  обсягом цього проходу. Див. HANDOFF `CLAUDE.md` щодо чесної межі етапу.

## Поточний стан (2026-07-26, досягнуто етап мінімального графічного конвеєра D3D11)

Новий крейт `crates/directx-graphics-vulkan` додає `ash` як **пряму**
залежність цієї робочої області (не поверх `opencuda-vulkan`, який,
підтверджено аудитом джерела, лише диспетчеризує обчислення). Він
реалізує реальний render pass, framebuffer та
`VkGraphicsPipelineCreateInfo`, повторно використовуючи вже згенерований,
уже успішно пройдений через `spirv-val` SPIR-V з
`translate_vertex_shader`/`translate_pixel_shader` вище (трансляція
шейдерів не реалізується повторно). `render_uniform_triangle_and_read_back`
малює один трикутник «на весь viewport» з єдиним рівномірним кольором
вершини, зчитує відрендероване зображення назад через host-visible
буфер стейджингу, а тест на реальному обладнанні
(`crates/directx-graphics-vulkan/tests/triangle_real_vulkan.rs`)
стверджує, що кожен зчитаний піксель відповідає прохідному кольору
вершини на реальному NVIDIA GT 730 цієї машини (`cargo test -p
directx-graphics-vulkan --test triangle_real_vulkan -- --nocapture`: 1
пройдено). Обсяг навмисно вузький: одна фіксована пара шейдерів, один
виклик малювання, без буфера глибини/текстур/swapchain/перевірки
інтерполяції кількох трикутників. Див. HANDOFF `CLAUDE.md` (продовження
2026-07-26) щодо повного чесного розкриття.

## Поточний стан (2026-07-25, вертикальний зріз Фази 1 узагальнено на 3 відомі шейдери)

`crates/directx-shader-translate` тепер виконує повний вертикальний
зріз для **трьох конкретних відомих шейдерів** (`vector_add.hlsl`,
`vector_mul.hlsl`, `vector_sub_bounded.hlsl`): розбір DXBC -> вузьке
декодування підмножини опкодів SM5.0 -> кодогенерація SPIR-V (через
`rspirv`) -> реальна диспетчеризація Vulkan (`opencuda-vulkan`
`open-cuda`) -> числова відповідність еталонній реалізації CPU,
перевірено на реальному NVIDIA GT 730 цієї машини. **Це все ще не
загальний декодер SM5.0-у-SPIR-V** — див. «Не реалізовано» нижче.

- `parse_dxbc` (Фаза 0): інтроспекція контейнера/чанків DXBC (наявність
  RDEF/ISGN/OSGN/SHEX), без змін від оригінального фронтенду.
- `spirv_gen::translate_shader` (Фаза 1, узагальнено 2026-07-25):
  розпізнає 3 форми опкодів, фактично випромінені `fxc.exe`, усі з
  спільним скелетом (`dcl_globalFlags` -> опційно `dcl_constantbuffer`
  -> 3x `dcl_uav_structured` -> `dcl_input` -> `dcl_temps` ->
  `dcl_thread_group` -> опційно `ult`+`if` -> 2x `ld_structured` ->
  `add`/`mul` -> `store_structured` -> опційно `endif` -> `ret`):
  - `vector_add.hlsl`: `add`, без перевірки меж.
  - `vector_mul.hlsl`: `mul` замість `add`.
  - `vector_sub_bounded.hlsl`: `add` з прапорцем `negate` на першому
    операнді джерела (підтверджено дампом реального виводу `fxc.exe` —
    `fxc` оптимізує `a - b` в `add dest, -b, a`, а не випромінює
    спеціальний опкод `sub`), плюс реальна перевірка меж
    `if (id.x < N)` (`ult` проти константного буфера + `if`/`endif`),
    що випромінений SPIR-V реалізує через справжній
    `OpSelectionMerge`/`OpBranchConditional`, використовуючи
    push-константу `n` для порівняння.
  Будь-яка інша форма опкода/операнда відхиляється через
  `SpirvGenError::UnsupportedShader`, а не мовчки перекладається
  неправильно. Точки прив'язки UAV, розмір групи потоків, оператор та
  наявність перевірки меж — усе видобувається з реального розібраного
  DXBC, а не жорстко закодоване. `translate_vector_add_shader`
  залишено як тонкий зворотно-сумісний псевдонім для `translate_shader`.
- `tests/vector_add_real_vulkan.rs`, `tests/vector_mul_real_vulkan.rs`,
  `tests/vector_sub_bounded_real_vulkan.rs`: кожен диспетчеризує свій
  транслейтований SPIR-V через реальний `opencuda-vulkan::VulkanDevice`
  `open-cuda` (`ash`, фіча `real-vulkan`) і перевіряє вивід GPU проти
  еталонної реалізації CPU для 256 елементів (епсилон 1e-3/1e-2).
  Тест перевірки меж додатково диспетчеризує 320 потоків з логічною
  кількістю елементів 256 і стверджує, що елементи 256..320 ніколи не
  записуються (залишаються значенням-сентинелом), доводячи, що гілка
  `if (id.x < N)` у згенерованому SPIR-V справді контролює виконання, а
  не лише компілюється.
- `examples/dump_shex.rs`: невеликий самостійний інструмент
  (`cargo run -p directx-shader-translate --example dump_shex -- <path.dxbc>`)
  використаний під час цієї сесії для перегляду реальних потоків
  опкодів SHEX перед написанням підтримки декодера для них; залишений
  для майбутньої роботи над узагальненням опкод-за-опкодом.

**Із моменту написання заголовка цього розділу**, додано 4-й шейдер з
одиничною операцією (`vector_div.hlsl`, простий `div`) до
`translate_shader` за тим самим точним шаблоном, і — нещодавніше —
справді інший клас патерну, `spirv_gen::translate_chain_shader`, додано
поряд з ним (не замінюючи його): він декодує реальне дерево виразів
регістрів послідовних бінарних операцій (add/mul, без керуючого потоку)
замість однієї фіксованої операції, перевірено проти нещодавно
скомпільованого шейдера, реальний SHEX якого виявився повторно
використовував компоненти одного тимчасового регістру через CSE fxc,
замість оголошення додаткових тимчасових регістрів. Див. запис HANDOFF
«продовження 9» від 2026-07-25 у `CLAUDE.md` щодо повного, актуального
опису (цей розділ залишено як спочатку написаний для історичної
точності щодо стану станом на середину дня 2026-07-25).

## Не реалізовано (чесний обсяг)

- **Загальне декодування інструкцій SM5.0.** Оброблено лише 3 форми
  опкодів вище; будь-який інший обчислювальний шейдер D3D11 (інший
  розклад ресурсів, інший керуючий потік, інші вбудовані функції, більше
  однієї перевірки меж, `div`/`sub` як реальна операція замість
  негованого `add` тощо) відхиляється, а не перекладається неправильно.
  Створення справжнього загального декодера (або впровадження/
  портування наявного, напр. детальніше вивчаючи підхід
  `dxbc-spirv`/`dxil-spirv`) залишається справжнім наступним етапом.
- **DXIL (Shader Model 6+, D3D12): вертикальний зріз `vector_add.dxil`
  тепер завершено наскрізно, на реальному обладнанні — але все ще лише
  для цієї однієї відомої форми шейдера, не загального SM6.0.**
  `resolve_type_table`/`decode_function_instructions`/
  `resolve_vector_add_dxil_calls` у `dxil.rs` декодують реальні записи
  `TYPE_BLOCK`/`FUNCTION_BLOCK`/`VALUE_SYMTAB_BLOCK` проти
  задокументованих кодів LLVM і розшифровують усі 7 записів `Call` до
  їхнього реального значення `dx.op.*` (`CreateHandle`/`ThreadId`/
  `BufferLoad`/`BufferStore`, з точками прив'язки UAV).
  `translate_dxil_vector_add_to_spirv` (нове) передає цей розв'язаний
  вивід у спільний `emit_spirv_for_kernel` `spirv_gen.rs` (винесений із
  `emit_spirv` шляху DXBC, щоб обидва бекенди випромінювали з одного
  шляху коду), щоб виробити реальний SPIR-V, який
  `tests/vector_add_dxil_real_vulkan.rs` диспетчеризує на реальному
  NVIDIA GT 730 цієї машини через `opencuda-vulkan` і перевіряє
  відповідність еталонній реалізації CPU `a[i]+b[i]` для всіх 256
  елементів — та сама ретельність, що й тест DXBC `vector_add`.
  **Розмір робочої групи тепер справді видобувається, а не жорстко
  закодований**: `extract_numthreads_from_metadata` (`dxil.rs`) проходить
  реальний шлях `METADATA_BLOCK` `dx.entryPoints` -> кортеж на кожну
  точку входу -> `ShaderProperties` -> `kDxilNumThreadsTag` (=4,
  підтверджено проти джерел `DxilMetadataHelper.h`/`.cpp` Microsoft
  `DirectXShaderCompiler`) і розв'язує вузол `{x,y,z}` проти реального
  списку значень модуля, даючи `(64,1,1)` з реальних байтів
  `vector_add.dxil` — відомий жорсткий код із попереднього запису
  закрито, і синтетичний регресійний тест доводить, що логіка
  видобування повертає *інше* значення при різних метаданих (не просто
  «завжди повертає 64,1,1»). Будь-яка інша форма опкода/операнда
  (інша операція, кілька базових блоків, перевірки меж) досі
  відхиляється, а не перекладається неправильно. Підтримка списку
  команд D3D12/купи дескрипторів/кореневого підпису (шар над
  трансляцією шейдерів) незачеплена.
- **Декодер DXBC узагальнено за межі 4 фіксованих форм із одинарними
  операціями: тепер обробляє ланцюжки послідовних бінарних операцій
  (без керуючого потоку) через справжнє дерево виразів регістрів, а не
  5-ту жорстко закодовану форму.** `spirv_gen::translate_chain_shader`/
  `decode_chain_shape` проходять `ld_structured`/`add`/`mul`/
  `store_structured` і будують справжнє дерево виразів, ключоване
  (тимчасовий регістр, компонент), так що обробляє 1 операцію, 2
  операції або N операцій однаково — перевірено проти нещодавно
  скомпільованого реального шейдера (`vector_add_mul_chain.hlsl`,
  `t = A[i]+B[i]; Out[i] = t*A[i]`), реальний SHEX якого виявився
  повторно використовував компоненти `.x`/`.y` одного тимчасового
  регістру (fxc CSE-нув повторне завантаження `A[i]` замість повторного
  видання `ld_structured`) — справжнє, непередбачене відкриття, яке
  декодер на основі дерева обробляє без додаткових випадків.
  Диспетчеризовано та перевірено на реальному NVIDIA GT 730 проти
  еталонної реалізації CPU `(a[i]+b[i])*a[i]`. `sub`/`div` всередині
  ланцюжка навмисно все ще відхиляються (їхня семантика порядку
  операндів перевірена лише для випадку одиничної операції). Оригінальні
  4 форми з одинарними операціями незачеплені і досі проходять без змін.
- **Графічний конвеєр D3D11: розбір контейнера DXBC підтверджено
  працюючим для VS/PS, але немає кодогенерації SPIR-V, растеризатора,
  жодного реального трикутника, відрендереного на екрані.** Повний
  конвеєр (растеризатор, семплінг текстур, стан бленду, output-merger)
  залишається поза обсягом; так само й розширення вузького декодера
  форм опкодів `spirv_gen` для розуміння `dcl_output_siv`/
  `dcl_input_ps`/режимів інтерполяції.
- Цілі родини PlayStation — явно поза обсягом; див. `CLAUDE.md` щодо
  правового обґрунтування/обґрунтування ToS.
