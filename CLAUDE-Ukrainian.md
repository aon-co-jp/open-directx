## Роль цього проєкту

Кросплатформовий шар сумісності DirectX (D3D9/10/11/12), метою якого є
запуск наявних застосунків/ігор, написаних для API DirectX, доступного
лише на Windows, на Linux, Android, а згодом і на macOS та родині
PlayStation.

2026-07-25, за явним вибором користувача, проєкт зобов'язався
переслідувати **справжній зворотний шар сумісності** (запуск
немодифікованих бінарних файлів/шейдерів Windows DirectX на інших ОС),
а не раніший альтернативний варіант «надання DirectX-подібного API
поверх Vulkan як спільної основи».

## Виправлення технічного позиціонування (2026-07-25, важливо)

Раніша оцінка (2026-07-23) вважала, що DXVK/vkd3d-proton/MoltenVK
транслюють лише в один бік (DirectX → Vulkan/Metal) без реального
прикладу зворотного напрямку, і тому були поганим технічним вибором. Це
було **змішанням двох різних осей** і виправлено:

- DXVK/vkd3d-proton (технологія, що стоїть за Proton від Valve /
  сумісністю ігор DirectX на Linux Steam) та CrossOver/Whisky на базі
  MoltenVK (macOS) — реальні, працюючі приклади саме тієї зворотної
  сумісності, якої хоче користувач: запуск реальних наявних бінарних
  файлів/ігор DirectX (API лише для Windows) без змін на Linux/macOS.
- **Напрямок трансляції** («виклики DirectX транслюються у виклики
  Vulkan») та **напрямок досвіду кінцевого користувача** (чи
  застосунок DirectX, орієнтований на Windows, справді працює на
  Linux/macOS) — це окремі осі — те, що перший орієнтований на Vulkan,
  не заважає другому правильно досягти «DirectX працює на іншій ОС».
- Тому використання Vulkan як внутрішнього бекенду виконання не
  суперечить переслідуванню справжнього зворотного шару сумісності —
  DXVK тощо є саме таким прецедентом. Цей проєкт застосовує той самий
  підхід: перехоплення викликів API D3D + трансляція байткоду шейдерів
  DXBC/DXIL під час виконання → виконання через Vulkan.

## Обсяг та чесна дорожня карта

**Фаза 0 (поточна, стадія дизайну/дослідження)**:
- Дослідити структуру DXBC/DXIL (формати байткоду шейдерів DirectX).
- Вивчити архітектуру наявних реалізацій OSS (DXVK, vkd3d-proton,
  [dxil-spirv](https://github.com/HansKristian-Work/dxil-spirv) —
  фактичний інструмент трансляції DXIL→SPIR-V, який використовує
  vkd3d-proton, SPIRV-Cross, naga), щоб уникнути винаходу колеса та
  запозичити перевірені дизайнерські рішення.
- Виокремити реалістичний обсяг MVP: **повний графічний конвеєр
  (растеризатор, семплер текстур, стан бленду тощо) наразі поза
  обсягом.** Почати з вертикального зрізу, що охоплює лише
  диспетчеризацію D3D11 Compute Shader (DirectCompute) — один простий
  обчислювальний шейдер, справді транслейтований з DXBC/DXIL у SPIR-V,
  диспетчеризований через `opencuda-vulkan` `open-cuda`, і перевірений
  на числову відповідність еталонній реалізації CPU. Робота над
  графічним конвеєром розпочнеться як наступна фаза лише після того, як
  цей вертикальний зріз доведено робочим.

**Фаза 1 і далі (ще не розпочато)**:
1. Вертикальний зріз D3D11 Compute Shader (трансляція
   DXBC/DXIL→SPIR-V + диспетчеризація Vulkan).
2. Мінімальний графічний конвеєр D3D11 (вершинні/піксельні шейдери +
   базова растеризація).
3. Підтримка D3D12 (списки команд, купи дескрипторів, кореневі
   підписи).
4. Підтримка Android (сам Vulkan нативний для Android, тож більшість
   ресурсів Linux мають бути придатними для повторного використання —
   але, ймовірно, знадобиться шар емуляції Win32/COM, еквівалентний
   Wine; у такому випадку варто розглянути співпрацю/повторне
   використання самого проєкту Wine).
5. Підтримка macOS / iPhone / iPad (через MoltenVK, той самий підхід,
   що й CrossOver/Whisky; iPhone/iPad вимагає Apple Developer Program
   для офіційного поширення — нативне виконання на неофіційному
   обладнанні неможливе, те саме обмеження, визначене в дослідженні
   `dream-os`).
6. Різні системи родини UNIX (BSD тощо) — ймовірно, здатні повторно
   використати більшість шляху Linux залежно від підтримки Vulkan (ще
   не досліджено).

## Базові проєкти (за вказівкою користувача, 2026-07-25)

- **[open-cuda](https://github.com/aon-co-jp/open-cuda)**: використовує
  `opencuda-vulkan` (бекенд виконання Vulkan Compute, перевірений на
  реальному обладнанні NVIDIA GT 730) як бекенд виконання шейдерів.
  Планує повторно використати абстракцію
  `opencuda-core::GpuDevice` (alloc/memcpy/launch_kernel) як є,
  передаючи транслейтовані з DXBC/DXIL у SPIR-V ядра як
  `KernelSource::SpirV` (точні деталі API потрібно підтвердити проти
  `opencuda-core`). Відрізняється від `opencuda-directx` (бекенд D3D12
  лише для Windows, Фаза 1&2 вже реалізована) — той запускає DirectX
  нативно *на* Windows, протилежний напрямок від цього проєкту (що
  запускає DirectX *на інших ОС*).
- **[aruaru-llm](https://github.com/aon-co-jp/aruaru-llm)**: наразі
  немає прямої технічної залежності (aruaru-llm — сервіс висновків LLM;
  цей проєкт — шар сумісності графічного API). Точний намір за
  переліком aruaru-llm як «бази» в інструкції користувача не
  підтверджено — можливо, означає слідування спільному шаблону сервісу
  «клон-техніка» (напр. застосування шаблону управлінського API у стилі
  `TenantRegistry` до якоїсь управлінської поверхні цього проєкту,
  наприклад сервера кешу трансляції). Буде оновлено, коли будуть
  визначені конкретні точки інтеграції.

## Політика розробки (загальнозведений підсумок екосистеми)

- Реалізація на основі Rust. Використовує крейт `windows` (Windows API)
  та прив'язки Vulkan (`ash` тощо, відповідно до того, що використовує
  `opencuda-vulkan`).
- «Ніколи не повідомляти про завершення лише на основі успішної
  перевірки типів/збірки» — повідомляти про щось як робоче лише після
  фактичної трансляції реального байткоду DXBC/DXIL, диспетчеризації
  через реальний Vulkan та підтвердження числової відповідності
  еталонній реалізації CPU на реальному обладнанні (дисципліна на рівні
  всієї екосистеми).
- Нереалізовані/заглушкові функції ніколи не повинні хибно сигналізувати
  «підтримується» (наслідуючи шаблон `supports_dxil()` `opencuda-directx`).
- Підтверджувати з користувачем перед будь-яким рішенням, що включає
  нові файли, нові крейти, нові репозиторії, або судженнями щодо
  найменування/розташування (урок з 2026-07-23, див. `CLAUDE.md`
  `open-raid-z`).

  точно, а напівпрозорий квадрант дає точний альфа-змішаний
  композитний колір, передбачений стандартною формулою «over». Уся
  робоча область: `cargo build`/`clippy` чисто (0 попереджень);
  `cargo test --workspace --release` проходить усі 33 тести на
  реальному обладнанні + 56 модульних тестів, без регресій. Чесне
  розкриття: черезрядкові PNG та PNG з 16 бітами на канал фактично не
  протестовано (лише покладено на автоматичну обробку крейту `png`);
  `directx-graphics-window` (демо реального вікна) ще не викликає цей
  завантажувач (все ще текстура суцільного кольору 1x1).

- **2026-08-08 (продовження 11): Реалізовано альфа-блендинг
  (напівпрозорі спрайти), перевірено на реальному обладнанні Windows +
  Linux.** Стандартний альфа-блендинг «over» увімкнено в побудові
  конвеєра `render_sprites_and_read_back`
  (`SRC_ALPHA`/`ONE_MINUS_SRC_ALPHA`/`ADD`). Оскільки `src.a=1.0`
  чисельно еквівалентно `blend_enable=false`, підтверджено, що всі
  наявні тести непрозорих спрайтів дають ідентичні результати
  (неруйнівна, адитивна зміна). Новий тест перевірив результат
  стандартної формули «over» на реальному обладнанні, обидві ОС
  збіглися точно. Чесне розкриття: цей блендинг увімкнено лише в
  позаекранному шляху `render_sprites_and_read_back` —
  `directx-graphics-window` (демо реального вікна) ще не оновлено
  відповідно; підтримується лише блендинг «over» (без адитивного/
  мультиплікативного режимів); взаємодія тесту глибини/порядку
  блендингу не перевірена (цей прохід не має буфера глибини, лише 2D
  спрайти).
